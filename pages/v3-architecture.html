It holds the device registry, stored data, alerts, tasks, manufacturing records, web console, and services used to manage edge nodes. - Edge nodes run next to equipment and can host the Nova Vector Edge Agent, EdgeX Foundry services, Edge AI runtime, and a local operator console. IoT devices can send data to the platform, while industrial adapters can connect outward to controllers, building systems, and network equipment. image: /assets/img/v3/architecture/01-high-level.png image_alt: High-level Nova Vector architecture showing platform, edge nodes, field equipment, users, and external systems caption: High-level deployment model from field equipment and edge nodes to the central Nova Vector platform. - eyebrow: Platform building blocks heading: Separate access, adapters, messaging, services, storage, and operations tooling paragraphs: - The platform uses nginx as the web entry point, Keycloak for user identity, protocol adapters at the device boundary, NATS and Redis for internal messaging patterns, PostgreSQL and TimescaleDB for operational and time-series data, and object storage for approved artifacts. - Operational modules—including alerts, tasks, manufacturing, process simulation, edge management, AI, dashboards, automation, and APIs—share the same device, channel, identity, and event foundation without being collapsed into one application. image: /assets/img/v3/architecture/02-platform.png image_alt: Nova Vector platform building blocks caption: Platform services are separated by responsibility and connected through documented interfaces. - eyebrow: Telemetry path heading: Normalize incoming readings and keep the route observable paragraphs: - Device and adapter traffic enters through the supported protocol path, is normalized into the platform reading format, distributed to interested services, and written to time-series storage. - Device profiles can decode vendor payloads into normalized readings for storage and visualization. Current architecture documentation distinguishes these decoded readings from the original readings used by the alert engine. image: /assets/img/v3/architecture/03-telemetry-path.png image_alt: Nova Vector telemetry flow from devices through adapters and messaging to storage and applications caption: Telemetry follows a defined path from connection adapters through messaging, processing, and storage. - eyebrow: Events and commands heading: Keep record changes, alerts, schedules, and device commands explicit paragraphs: - Record changes are distributed through Redis Streams to services that maintain their own operational copy. Alert outcomes and device commands travel through NATS, while scheduled jobs and heartbeats feed the same command path. - Edge nodes use their MQTT control channel for status and signed deployment commands. A command request is observable as a software operation; network and physical device execution remain separate concerns. image: /assets/img/v3/architecture/04-events-commands.png image_alt: Nova Vector events and commands architecture caption: Events, alerts, schedules, and commands use separate documented paths. - eyebrow: Device authentication heading: Authenticate device and edge traffic at the connection boundary paragraphs: - Device identity and connection checks depend on the selected protocol and adapter. Edge nodes use their registered device identity for telemetry and status, while edge-management commands carry signed command tokens. - Transport security is finalized per deployment. MQTT over TLS is available, but the standard installation does not publish it by default. image: /assets/img/v3/architecture/05-device-authentication.png image_alt: Nova Vector device authentication flow caption: Device authentication is applied at the relevant protocol and adapter boundary. - eyebrow: User authentication heading: Use Keycloak-backed sign-in, roles, and groups across the web platform paragraphs: - Users sign in through Keycloak. Platform services validate the active token and use roles, permissions, and group ownership to control access to records and modules. - Two-factor authentication is available but is not enforced by default. Company-directory integration, password policy, audit requirements, and administration-console restrictions are finalized for each production project. image: /assets/img/v3/architecture/06-user-authentication.png image_alt: Nova Vector user authentication and authorization flow caption: User access is based on Keycloak identity, roles, permissions, and groups. - eyebrow: Current deployment scope heading: Treat resilience and infrastructure choices as project architecture paragraphs: - The standard Docker Compose installation runs one instance of each service on one server. Industrial adapters and the batch writer can scale independently, but a fully redundant installation is designed per project. - Kubernetes is delivered as a project service; standard whole-platform manifests or Helm charts are not shipped today. Isolated networks are prepared per project rather than through a packaged offline installer. points: - No built-in HA for database, Redis, NATS, Keycloak, or MQTT broker in the standard single-server deployment - NATS is used without persistence; missed messages are not replayed automatically - Edge nodes do not buffer telemetry while the platform is unreachable - Data retention, backups, TLS exposure, VPN/routing, and production hardening are defined per project related: - label: Platform Overview url: /industrial-iot-platform/ - label: Nova Edge url: /edge-computing-platform/ - label: Integrations url: /integrations/ ---
