Understanding those boundaries makes integrations easier because it clarifies which service owns a resource and how data or commands move between components. - The architecture documentation describes the high-level platform, internal service layers, telemetry path, event and command flow, device authentication, and user authentication. Channels carry messages. Profiles describe device types, metrics, properties, and decoding behavior. Production, alerts, tasks, commands, and process state build on top of those lower-level resources. - Integrations are easier to maintain when they use those platform relationships instead of inventing a second naming and identity scheme outside Nova Vector. image: /assets/img/v3/features/02-devices-and-live-data/profile-metrics.png image_alt: Nova Vector device profile metrics caption: Device profiles provide the semantic layer between protocol data and application-level meaning. - eyebrow: APIs and messaging heading: Choose the interface that matches the integration pattern paragraphs: - REST is the primary documented resource interface. MQTT, HTTP, WebSocket, and internal event flows serve different real-time or asynchronous needs. Scheduled jobs and command resources provide a managed path for repeatable device actions. - The documented API surface should be preferred over direct database coupling because it preserves authorization, resource ownership, and service boundaries. image: /assets/img/v3/features/11-automation-and-integration/open-api.png image_alt: Nova Vector OpenAPI documentation for developers caption: OpenAPI provides the documented entry point for supported resource operations. - eyebrow: Edge development heading: Treat the site runtime as a managed part of the wider platform paragraphs: - Nova Edge can host EdgeX device services, application logic, local operator access, and Edge AI. The Edge Agent connects that site-side runtime to central node identity, software catalogs, rollout state, and audit information. - Supported service combinations and versions are deployment-specific. Developers should design against the approved bundle and node type for the project rather than assuming arbitrary EdgeX or container workloads can be deployed without qualification. image: /assets/img/v3/features/07-edge-management/node-state.png image_alt: Nova Vector edge node state for developers caption: Node state links site-side software with the central deployment model. - eyebrow: Failure behavior heading: Design for what happens when networks or services are unavailable paragraphs: - The current architecture uses core NATS without persistence, so messages missed during a restart or overload are not automatically replayed. Edge nodes also do not buffer telemetry while the central platform is unreachable. - Commands, API submissions, and persisted state should therefore be interpreted carefully: software acceptance of a request is not the same as guaranteed delivery to a remote site or atomic execution by physical equipment. image: /assets/img/v3/architecture/04-events-commands.png image_alt: Nova Vector event and command flow caption: Understanding asynchronous event and command paths is essential for reliable integration design. related: - label: Documentation url: /documentation/ - label: REST API url: /api/ - label: Architecture url: /architecture/ ---
