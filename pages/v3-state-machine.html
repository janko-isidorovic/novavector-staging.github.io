Nova Vector process models combine selected data sources with explicit states and guarded transitions, so the platform can tell whether equipment is running, idle, starved, blocked, stopped, or in another customer-defined condition. - Rules link machines to each other. Each machine's state drives the state of the line, and the line's state drives an andon board, so the reason behind a degraded line is visible on one diagram. image: /assets/img/v3/screens/process-machine-to-machine.png image_alt: Nova Vector process diagram with filler, capper, labeller, and packer linked by rules to the line state and the andon board caption: Rules link each machine's state to the line's state, and the line's state to the andon board. - eyebrow: Versioned logic heading: Know which rule caused every state change paragraphs: - Published process versions are immutable, so historical execution is interpreted against the exact logic that was active at the time instead of today's edited configuration. - Every state change is logged with its trigger, the values behind it, and the rule version that applied. The execution log exports to CSV for your own analysis. image: /assets/img/v3/features/05-process-simulator/execution-log.png image_alt: Nova Vector execution log listing state changes with their trigger, version, and the values behind each change caption: The execution log records each state change with its trigger and rule version. - eyebrow: Alerts heading: Detect a condition and preserve the evidence around it paragraphs: - Alert definitions watch configured values and no-data conditions. When the condition changes state, Nova Vector updates the affected device context and routes the result into notification and task workflows. Notifications are sent by e-mail to the configured recipients. - Alert limits are defined in the platform rather than hard-coded into a dashboard. This keeps the detection rule connected to the equipment that owns it and gives teams one place to inspect current and historical alert state. image: /assets/img/v3/features/04-alerts-notifications-and-tasks/alert-limits.png image_alt: Nova Vector alert-limit configuration for a device metric caption: Alert limits define the conditions the platform evaluates for a device or metric. - eyebrow: From alarm to work heading: Convert an abnormal event into something a person can own paragraphs: - An alert can create a task from a configured template. The task keeps its category, assignee, status, history, and the source context that caused it, so maintenance or support teams do not have to reconstruct the original event from another system. - Where configured, clearing the source alert resolves the related task automatically. A technician can scan an RFID badge at the machine to record arrival, so response and repair times are measured rather than estimated; the flow can be customized to match your maintenance process. image: /assets/img/v3/features/04-alerts-notifications-and-tasks/tasks-from-alerts.png image_alt: Nova Vector task list showing tasks created from alerts, with status, duration, assignee, and category caption: Alert-generated tasks keep the originating context and are tracked through resolution. - eyebrow: Task workflows heading: Run repeatable work from templates on shared boards paragraphs: - Inspections, changeovers, quality checks, and preventive maintenance run from templates with sub-tasks and recurring schedules. Kanban boards group work by status, category, or person, and kiosk boards put the same view on shop-floor screens. - Rules and blockers keep critical steps in order. A batch cannot be released while a check is still open, and selected status changes ask for a password signature and a reason. points: - Templates, sub-tasks, and recurring schedules - Boards by status, category, or person, with "my tasks" for everyone - Blockers and signed status changes for critical steps image: /assets/img/v3/screens/task-kanban-board.png image_alt: Nova Vector Kanban board with downtime, inspection, maintenance, and quality tasks by status, including blocked and overdue tasks caption: A line Kanban board with sub-task progress, owners, and blocked or overdue tasks. - eyebrow: Traceable response heading: Keep notification, task, and command behavior separate and observable paragraphs: - Notifications inform configured recipients, tasks represent owned work, and commands represent requests to act on a device. Keeping these separate makes it clear whether a condition was detected, whether somebody was assigned to it, and whether an automated action was requested. - Commands are executed asynchronously through the platform's command path. Persisting the software request does not imply that a remote controller or physical process acted atomically, which is an important distinction in industrial systems. image: /assets/img/v3/architecture/04-events-commands.png image_alt: Nova Vector event, alert, task, and command architecture caption: Alerts, tasks, notifications, schedules, and commands use explicit service paths rather than one hidden automation chain. related: - label: Process Simulation & Replay url: /industrial-simulation/ - label: Manufacturing url: /manufacturing/ - label: OEE & Downtime url: /manufacturing-oee-software/ - label: Platform Architecture url: /architecture/ ---
